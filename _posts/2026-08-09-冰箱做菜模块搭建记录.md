# 冰箱做菜模块搭建记录

---

## 背景

每天的灵魂拷问不是"今天吃什么"，而是"**冰箱里这些乱七八糟的，到底能做什么**"。

半根黄瓜、两个鸡蛋、一颗快蔫的番茄——扔了可惜，做菜又没思路，最后总是点外卖。
于是想在博客里加一个小工具：**把冰箱食材报给它，它告诉你今天能做啥、还缺啥、
多久能上桌**。

硬性约束有两个：

- GitHub Pages 只能托管静态文件，**没有后端、没有数据库**
- 自己不太做饭，所以菜谱必须**新手友好**：步骤要具体、要点要讲清、
  翻车点要提前预警

## 功能设计

### 核心流程

```
输入冰箱食材（打字联想 / 点选常用食材）
      ↓
实时匹配 88 道菜谱 → 打分 → 分档
      ↓
✅ 能做 / 🔶 差一点（缺料可替代）→ 购物清单自动汇总
      ↓
点开详情 → 做法步骤 + 翻车点 + 替代方案
```

### 匹配引擎：一句话公式

```
得分 = 主料命中 × 5 + 辅料命中 × 2 + 用掉的食材数 × 1 + 快过期食材命中 × 3
```

三个设计点值得说：

1. **主料/辅料分开权重**：缺辅料（葱、料酒）可以忍，缺主料（肉、蛋）这道菜就不成立。
   所以 `main` 是硬指标，`minor` 是软指标，缺了会显示"还差 料酒，可用 白酒 替代"。
2. **"清冰箱优先"是默认排序**：这个工具的第一使命不是推荐好吃的，而是**帮你把
   快过期的食材用掉**。长按食材可标记 ⭐ 快过期，被用到的菜直接顶到最前。
3. **替代方案（alt）**：`"料酒": ["白酒", "啤酒"]` —— 缺了料酒但冰箱有白酒，
   这道菜依然"能做"，并明确提示替换关系。这是实用性的大头。

### 分类与排序

- **工具筛选**：灶台 / 电饭煲 / 微波炉 / 空气炸锅 / 烤箱——没有空气炸锅的人，
  不应该看到空气炸锅菜谱。每个菜谱都声明 `tools`，前端按用户勾选过滤。
- **三种排序**：清冰箱优先 / 缺料最少 / 最快上桌。
- **万能公式兜底**：如果冰箱凑不出一顿正经饭，动态生成"XX 炒蛋"、"剩饭炒饭"、
  "冰箱大杂烩汤"这类通用方案，绝不让你空手而归。

## 数据设计

### 菜谱结构（recipes.json）

```jsonc
{
  "id": "potato-beef",
  "name": "土豆炖牛腩",
  "main": ["牛腩", "土豆"],          // 主料：缺了不成立
  "minor": ["姜", "八角", "生抽"],    // 辅料：可缺、可替代
  "alt": { "牛腩": ["牛肉"], "八角": ["十三香"] },
  "time_min": 75,
  "difficulty": 2,                    // 1=零基础 2=有点要求 3=需要技巧
  "tools": ["灶台"],
  "method": ["步骤1", "步骤2", "..."],
  "fail_points": ["一定要加热水，加冷水肉会变柴"],
  "note": "炖的时候不用管，适合边炖边干别的"
}
```

目前 **88 道菜谱、10 个类别**：零基础炒菜 14、快手菜 22、一锅炖/焖 12、
剩饭改造 7、电饭煲 6、面食主食 6、凉拌菜 7、微波炉 4、空气炸锅 4、汤 6。

### 两个数据层的细节

1. **别名归一化**：`西红柿→番茄`、`马铃薯/洋芋→土豆`、`上海青→油菜`，
   输入"马铃薯"和"土豆"匹配到同一道菜。这是"输入体验"的根基。
2. **`fail_points` 字段**：新手最大的痛点不是不会做，是"不知道为什么做出来不对"。
   每道菜 1~2 条翻车点预警，比多写 50 道菜更值钱。

## 纯静态架构：没有后端怎么存用户数据？

GitHub Pages 没有后端，用户的冰箱清单怎么持久化？方案是**分层处理**：

```
菜谱库（公共数据）─── fetch 静态 JSON，不占本地存储
用户状态（个人数据）── localStorage 单键全量 JSON
    ├─ uid：首次访问生成的 UUID，身份锚点
    ├─ fridge / urgent：冰箱清单 + 快过期标记
    ├─ tools / prefs：工具与偏好
    └─ eaten / favorites：最近做过（防重复推荐）与收藏
```

关键是**存储抽象层**：所有读写都走 `store.js` 一个文件（`load/save/export/import`），
业务代码不直接碰 localStorage。将来要上云同步（Supabase/Gist），只改这一个文件。
跨设备迁移靠两个逃生通道：**导出/导入 JSON 备份**、**URL 参数分享**
（`?fridge=土豆,鸡蛋` 直接带清单）。

## 踩坑记录

### 1. 菜单只显示图标，文字消失

上线后发现导航栏的"冰箱做菜"只剩图标，文字不见了。排查发现 NexT 主题的菜单
渲染分两个来源：

```html
<i class="fa fa-{{ site.menu_icons[itemName] }}"></i>   <!-- 图标：_config.yml 的 menu_icons -->
{{ __.menu[name] }}                                     <!-- 文字：语言包 _data/languages/ -->
```

`_config.yml` 里加了 `cook: /fridge-cook/`，图标从 `menu_icons` 正常取到；
但**菜单文字是从语言包翻译的**，`zh-Hans.yml` 里没有 `cook` 键，渲染结果为空字符串。
修复：语言包补 `cook: 冰箱做菜`（default.yml 同步补，防止其他语言环境再缺）。

### 2. `display: flex` 覆盖了 `hidden` 属性

详情弹层明明设了 `hidden`，却一直显示。原因是 CSS 里 `.fc-mask { display: flex; }`
的优先级高于 HTML `hidden` 属性的默认 `display: none`。修复一行：

```css
[hidden] { display: none !important; }
```

### 3. 推送被拒：远端有 Actions 自动提交

`git push` 报 `rejected (fetch first)`——忘了 stock-data 的 GitHub Actions
定时任务每天会自动 commit 新数据回来。`git pull --rebase` 合入后推送成功。
**这个仓库的 master 是"活的"**，推送前先 pull 是常态。

### 4. 本机直连 GitHub 超时

本机没配 git 代理，push 时直连 github.com 超时。本机 1080 端口有代理在跑，
用临时参数解决（不修改任何 git 配置）：

```bash
git -c http.proxy=http://127.0.0.1:1080 push origin master
```

### 5. 输入"土豆"，却推荐了"糖拌番茄"

发布后收到反馈：冰箱里只加了一个"土豆"，推荐列表里却冒出"糖拌番茄""白灼虾"这种和土豆毫无关系的菜。根因在分档逻辑——"差一点"（允许主料缺 1 个）的定义对单主料菜太宽松：`main: ["番茄"]` 的糖拌番茄只要缺番茄就是"差一点"，完全不要求推荐结果与用户食材有任何交集。

修复：推荐前加一道**交集门槛**——菜谱与用户食材至少命中 1 样（含替代命中）才进入推荐列表。现在输入"土豆"，只会看到空气炸锅薯条、土豆片炒肉这类真正用得上的菜。

### 6. 回归测试揪出的两个隐藏 bug

修交集门槛时顺手做了全流程回归，结果挖出两个"一直没被发现"的 bug：

- **localStorage 从未写入**：存储层 `load()` 返回的是深拷贝，业务代码改的是拷贝；而保存调用 `Store.update({})` 传的是空 patch——拷贝被修改、内部状态没变，`localStorage` 里始终是初始空状态，刷新页面食材就全没了。修复：业务层直接持有存储层内部引用（`Store.state()`），修改天然同步。
- **万能公式卡片渲染崩溃**：冰箱凑不出一顿正经饭时，兜底方案（"XX 炒蛋"、"冰箱大杂烩汤"）构造的卡片对象缺 `mainMiss`/`minorMiss` 字段，渲染时 `undefined.concat` 直接抛异常，兜底区一片空白。修复：补全字段 + 渲染层防御。

两个 bug 都是"路径平时走不到、一走到就崩"的类型——交集门槛修复后推荐变少了，反而更容易触发兜底路径，回归测试的价值就在这。

## 小结

- 纯前端 + 静态 JSON，在 Pages 上跑通了一个**真正有用的工具**，零后端成本
- 实用性的关键在于数据设计：主辅料分级、替代方案、翻车点，比炫酷的交互更值钱
- 推荐算法除了"分档准"，还要保证结果与用户食材**有交集**，否则再准的分档也会产出噪音
- 下一步：菜谱继续扩充（烤箱/烘焙、按菜系）、访客提交菜谱（GitHub Issue → Actions 合入）、
  以及把"做饭记录"做成数据可视化
